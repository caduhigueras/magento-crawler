# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Rust (edition 2024) CLI, `magento_crawler`, that warms Magento/Varnish cache. It reads URL lists from CSV files and requests each URL once per configured `X-Magento-Vary` cookie value, so every cache segment (customer group, store view, currency) gets warmed rather than only the anonymous one.

## Commands

CI (`.github/workflows/general.yml`) runs these three checks, and all must pass:

```bash
cargo test
cargo fmt --check
cargo clippy -- -D warnings   # warnings fail CI
```

- Build: `cargo build --release` produces `target/release/magento_crawler`
- Run locally: `cargo run`. You need a config file first (see below), and `input_dir` must exist or the binary panics.
- Run a single test: `cargo test <test_name>`. Tests are unit tests inside the modules. The `server.rs` ones drive the axum router with `tower::ServiceExt::oneshot`.
- Releases use cargo-dist (`dist-workspace.toml`, `.github/workflows/release.yml`). They build for Linux and macOS (x86_64/aarch64) and Windows x86_64. `release.yml` was generated by `dist`, but it also has a hand-written `build-amazonlinux2` job. That job builds inside an `amazonlinux:2` container and uploads a bare binary. `allow-dirty = ["ci"]` stops `dist` from overwriting the custom job, so keep that setting if you regenerate.

## Configuration

`configuration::get_configuration` loads the config only from `<dirs::config_dir()>/magento_crawler/config.toml`, e.g. `~/.config/magento_crawler/config.toml` on Linux. It panics if the file is missing. There is no repo-local config. The README has a full example.

- Env vars override file values. They use the prefix `APP_` and `__` as the nesting separator, e.g. `APP_APPLICATION__CONCURRENCY=50`.
- `APP_ENVIRONMENT` (`local` | `production`, default `local`) is **not** part of `Settings`. `email_sender::send` reads it directly. `local` sends over unauthenticated SMTP to `localhost:1025` (MailCatcher), and `production` uses the system `sendmail`.
- If you add a setting, update the struct in `configuration.rs` and also the README's example config and env-var list.

## Architecture

`main.rs` parses the clap subcommand (`run`, the default when none is given, or `serve`), loads the config and calls `app::run` or `server::serve`. `app::run` holds the whole file pipeline:

1. `file_manager::get_files_from_dir` lists the `.csv`/`.txt` files in `input_dir`, oldest first by mtime, skipping hidden files and symlinks. Each file is processed in turn.
2. `parse_csv_as_urls` reads a CSV with no header and one URL per line. It keeps only `http(s)` URLs whose host exactly matches the required `allowed_hosts` setting; other lines are logged and dropped. `crawler::prepare_url_for_crawl_job` builds the cross product of URLs × cookies. `reqwest_client::prepare_cookies` splits the comma-separated `cookies` setting and **prepends an empty cookie**, so every URL is also requested without a vary cookie.
3. The jobs run through a `futures::stream` with `buffer_unordered(concurrency)`. `crawler::crawl_page` sends one GET and then:
   - decides whether the response was cached (`crawler::is_cached`). If `cache_warmer_secret` is set, the client sends it as `X-Cache-Warmer` on every request and a hit is `X-Cache: HIT*`, which is added by the `custom.vcl` documented in the README. Otherwise a hit is `Age > 0`.
   - logs the request through `telemetry::log_response` (with `tracing`)
   - optionally sends a row for each request to `clickhouse_client::spawn_writer`. That single task, shared across the whole run, inserts rows into `crawl_logs` in batches (10k rows or every 5s) and logs failures without stopping the crawl. Rows use `crawl_id = "<file>_<YYYYmmddHHMM>"`.
   - sends transport failures (timeout, connection, other) to the error CSV and counts them in `Stats.failed`
   - sends 404/500/502/503 responses to the error CSV, **only for the empty-cookie request** so errors aren't duplicated per segment
   - returns `FollowUpAction::Sleep` on a 502 or 503. The caller then sleeps `sleep_timeout_seconds`, which holds only that stream slot, not the whole crawl. This is deliberate: the team tested a global pause and found it made crawls too slow, so don't "fix" it.
4. Error rows go through an mpsc channel to one writer task (`csv_writer::spawn_csv_writer`), which writes `<reports_folder>/YYYY/MM/<start>_errors_<file>`. All senders, including the original `csv_tx`, must be dropped and the handle awaited before the file is complete.
5. After a file is crawled, it is **moved** (renamed) to `<input_dir>/.history/YYYY/MM/<start>_<file>`. Input files are consumed, not left in place.
6. Once all files are done, if `send_email` is set, one HTML email is sent. It links each error report by swapping the `reports_folder` prefix for `reports_server` in the path.

`server::serve` (axum) is the long-running mode. It needs the optional `[server]` config section and a bearer token. `RequestDecompressionLayer` gunzips request bodies before the size limits apply.
- `POST /upload` streams the body to a hidden `.<name>.part` file in `input_dir`, rejects it if it has no crawlable URL, then renames it. The next `run` crawls it, since `serve` never crawls uploads itself.
- `POST /urls` validates the URLs and pushes them into an mpsc queue read by `live_crawler::spawn_live_crawler`. That single task builds the same (url × cookie) jobs with `crawler::crawl_job` and `buffer_unordered`, which is shared with `run`. It writes errors through `csv_writer::spawn_daily_csv_writer` (one file per day, flushed per row) and stops on shutdown, dropping queued URLs.

The crawler only runs in a controlled environment against the team's own servers, with fixed settings. That explains some shortcuts, such as unvalidated config. The reqwest client accepts invalid TLS certs on purpose (`danger_accept_invalid_certs`). Most failures `unwrap`/`expect`/panic instead of propagating errors.

## Observability stack (`.dashboard/`)

`docker compose up -d` in `.dashboard/` starts ClickHouse (HTTP on 8123) and Grafana (3000, admin/admin), both provisioned as code. You must set the credentials both in `docker-compose.yml` and in `docker/grafana/provisioning/datasources/clickhouse.yml`. `docker/clickhouse/init/001-init.sql` defines the schema: `crawl_logs`, plus a materialized view that fills `crawl_kpis`. The init SQL only runs against an empty data dir. If you change the `ClickHouseLog` struct in `telemetry.rs`, the init SQL must change with it, and so may the Grafana dashboard JSON.
